## Build and test

Run from the repository root:

```powershell
dotnet restore AriaGui.slnx -p:Platform=x64 --locked-mode
dotnet build AriaGui.slnx --no-restore -p:Platform=x64
dotnet test tests/AriaGui.Core.Tests/AriaGui.Core.Tests.csproj --no-build --no-restore
dotnet test tests/AriaGui.Application.Tests/AriaGui.Application.Tests.csproj --no-build --no-restore
dotnet test tests/AriaGui.Infrastructure.Tests/AriaGui.Infrastructure.Tests.csproj --no-build --no-restore
```

Or use `scripts/Verify.ps1`. This script stops on the first failed command. Packages need network access on the initial restore. Changing package references intentionally requires a normal restore to regenerate lock files before locked verification.

The solution maps the WinUI project to x64. The portable libraries/tests retain their default Any CPU configuration. Build and run the app with the same `Platform=x64` value so the executable and generated launch files come from matching folders.

## Run without Developer Mode

```powershell
dotnet restore src/AriaGui.App/AriaGui.App.csproj -p:Platform=x64 -p:AriaGuiUnpackaged=true
dotnet build src/AriaGui.App/AriaGui.App.csproj --no-restore -p:Platform=x64 -p:AriaGuiUnpackaged=true
dotnet run --project src/AriaGui.App/AriaGui.App.csproj --no-build --no-restore -p:Platform=x64 -p:AriaGuiUnpackaged=true --launch-profile "AriaGui.App (Unpackaged)"
```

`scripts/Run.ps1 -Unpackaged` wraps those commands. The explicit fallback uses the supported unpackaged WinUI configuration and includes Windows App SDK runtime files. It does not change Windows settings or register an MSIX package. The .NET runtime is still framework-dependent and must be installed.

Executable output:

```text
src/AriaGui.App/bin/x64/Debug/unpackaged/net10.0-windows10.0.26100.0/win-x64/AriaGui.App.exe
```

## Run with package identity

Enable Developer Mode yourself in Windows Settings → System → For developers. Then:

```powershell
dotnet restore src/AriaGui.App/AriaGui.App.csproj -p:Platform=x64
dotnet build src/AriaGui.App/AriaGui.App.csproj --no-restore -p:Platform=x64
dotnet run --project src/AriaGui.App/AriaGui.App.csproj --no-build --no-restore -p:Platform=x64 --launch-profile "AriaGui.App (Package)"
```

`scripts/Run.ps1` wraps those commands. The template's WinApp integration registers a local development identity and launches the app. This is a development deployment smoke test, not a signed production installer. Signing, clean-machine installation, and upgrade tests remain Phase 7 work. Microsoft's [WinUI quickstart](https://learn.microsoft.com/en-us/windows/apps/get-started/start-here) and [template documentation](https://github.com/microsoft/WindowsAppSDK/blob/main/dev/Templates/Dotnet/README.md) describe the underlying workflow.

If the packaged launch reports that Developer Mode is disabled, use the unpackaged command while leaving packaged verification pending. No Windows settings were changed by this implementation.

## Debug in Visual Studio

1. Open `AriaGui.slnx` in Visual Studio 2026.
2. Set `AriaGui.App` as the startup project; choose Debug and x64.
3. With Developer Mode enabled, select the package launch profile and press F5.
4. Place a breakpoint in `App.OnLaunched` before constructing `MainWindow`, then restart debugging. Inspect the services being registered.
5. Place a second breakpoint in `DownloadCoordinator.AddAsync`, continue, and click Add. Inspect the URL, job ID, and engine ID.

If a WinUI project type is unavailable in Visual Studio, use the Visual Studio Installer's WinUI application development workload; command-line builds here already work. If staying unpackaged, run the preview with the script, then use Debug → Attach to Process → `AriaGui.App.exe` with the managed .NET debugger and break on an Add action.

Breakpoint exercises are documented learning steps; they are not claimed as automated verification.

## Why these files exist

- `AriaGui.slnx` groups all projects for Visual Studio and command-line builds.
- Each `.csproj` declares one project's dependencies and target framework.
- `Directory.Build.props` applies shared compiler settings and lock-file generation.
- `App.xaml` loads WinUI's control resources; `App.xaml.cs` creates and connects services.
- `MainWindow` supplies the native window and hosts the download page.
- `Package.appxmanifest` declares development package identity and Windows requirements.
- `Properties/PublishProfiles/win-x64.pubxml` selects self-contained release packaging; normal builds do not load it implicitly. Use `scripts/Package.ps1` to also collect notices and validate the resulting MSIX.
- `obj` and `bin` contain generated code and compiled outputs; do not edit or commit them.

Only x64 is configured for the app. The real-engine tests require Windows and launch isolated child processes in temporary folders on dynamically selected loopback ports. Their timeout tests use `AriaGui.EngineFixture`, a tiny test executable that can deliberately remain unresponsive or exit early; it is never shipped with the app.

## Engine files and diagnostics

For an installed MSIX, the runtime folder is the package's `LocalState\Engine`, resolved explicitly by `AppDataPaths`. The unpackaged paths below remain the development preview's paths; there is no automatic cross-import. Read [Phase 7](PHASE_7.md) for package building/signing, and [release acceptance](RELEASE_ACCEPTANCE.md) before upgrading/uninstalling.

The app copies the pinned engine from `vendor/aria2` into the build output. Startup validates its SHA-256 hash. `vendor/aria2/provenance.json` and `scripts/Get-Aria2.ps1` record and reproduce acquisition; normal builds need no separate engine installation.

Runtime files live under `%LOCALAPPDATA%\AriaGUI\Engine`, outside the executable folder. Windows access rules restrict that folder to the current user and SYSTEM. The app uses fixed loopback port **16800**. If another program holds it, the engine panel reports the conflict and does not attach to or stop that program. Port configuration can become a settings feature later.

| File | Purpose |
| --- | --- |
| `app.lock` | Exclusive file handle acquired before startup; enforces one app per user/data folder |
| `engine.lock` | Exclusive engine-manager handle; prevents two owners |
| `aria2.conf` | Generated configuration with a fresh RPC secret; removed after clean shutdown |
| `engine.owner.json` | PID, process start time, session ID, paths, and port; contains no secret |
| `engine.checkpoint.json` | Pointer to the retained session, independent of live process ownership |
| `sessions/session-<id>.txt` | Engine checkpoint for unfinished transfers, retained after shutdown |
| `downloads.db` | Jobs, attempts, files, operation history, and saved queue policy |
| `preferences.json` | Validated app theme and default download folder; bounded atomic file |
| `Backups/downloads-before-upgrade-*.db` | Verified private SQLite backup made before migrating an existing schema |
| `engine.log`, `engine.log.previous` | Bounded diagnostics with the RPC secret and HTTP/FTP/SFTP URLs redacted |

Do not copy `aria2.conf` into bug reports. Diagnostics omit request bodies and raw RPC errors. Future downloaded URLs can appear in engine session files; treat the private runtime folder as sensitive app data.

Since Phase 5, Close hides to a verified tray icon. Explicit Exit checkpoints history/session, requests engine shutdown, and exits. A shutdown deadline falls back to terminating only the process the manager started or fully verified and adopted. The engine is launched without inherited handles or captured standard-I/O pipes and can survive a GUI crash. `stop-with-process` is no longer set. If the tray cannot register, Close leaves the window reachable.

Startup can adopt a surviving recorded engine only after process identity, previous owner, protected configuration, and authenticated session checks agree. Otherwise, a dead engine's validated session can restore known unfinished jobs into a new process. Unknown records are preserved and reported. See [Phase 5](PHASE_5.md) for the recovery trace and failure matrix, [Phase 3](PHASE_3.md) for SQLite, and [Phase 4](PHASE_4.md) for queue commands.

Phase 6 uses compact batch progress queries, slower inventory reconciliation, idle backoff, and coalesced runtime UI callbacks. Startup materializes live work plus 100 recent terminal records; history browsing reads bounded SQLite pages. See [Phase 6](PHASE_6.md) for the code trace, scale-test budgets, and native verification limits. `artifacts/phase6-profile.json` is regenerated by the 100-live/10,000-history application test. Close any existing preview through its explicit Exit action before rebuilding its unpackaged output. Avoid building a test project's output while its test host is running: Windows locks loaded DLLs.

## SQLite schema and migrations

`downloads.db` lives beside the engine's private runtime files. The app applies versioned EF migrations at startup, reports storage failures, and preserves an unreadable database for diagnosis. Phase 7 creates and verifies an online SQLite backup before upgrading existing schemas and rejects unknown newer schema versions. Database work is serialized through one background execution boundary with a fresh context per unit of work. Never edit a generated migration already applied to shared/released data; introduce a new migration for subsequent changes.

To install the workspace-local tooling and generate a future migration intentionally:

```powershell
dotnet tool install dotnet-ef --version 10.0.9 --tool-path .tools/ef
.\.tools\ef\dotnet-ef.exe migrations add YourChangeName --project src/AriaGui.Infrastructure --startup-project src/AriaGui.Infrastructure --output-dir Persistence/Migrations
```

Use the install command only if the local tool is missing. The design-time factory uses a design-only connection string and does not open the user's runtime database when generating migrations. Inspect generated source and the model snapshot, then run the tests. Ordinary users/builds do not need EF tooling.

The explicit native SQLite bundle pin overrides EF's older default bundle after restore reported a vulnerability. Do not remove that override without checking the resolved native version and advisory status. Package lock files record the reviewed dependency graph.
