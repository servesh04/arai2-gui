## Header/body mismatch: what the code does and does not prove

Let `C` be canvas leading edge, `I` the measured native row-template leading inset, and `Pj` the cumulative effective widths before column j. Once both runtime grids are configured, their column starts are approximately `header = C + 38 + Pj` and `row = C + I + 32 + Pj`. Their text starts add the same 8. Thus an origin difference is `6 − I`, independent of column index, before common rounding. Zero ListViewItem Padding does **not** prove I is zero. The hardcoded 38 can only match if the effective inset happens to be 6; no source contract guarantees that.

The 80 canvas allowance is not a measured gutter/inset/scrollbar budget. Header padding consumes 54, leaving 26 beyond the width sum; the row consumes 32 plus unknown native insets/scrollbar. This creates independent unused-space accounting, but absolute configured columns do not automatically stretch to consume it. A large Size-under-Name discrepancy is therefore not explained by a six-DIP gutter difference alone.

Before RowLoaded configuration, body XAML uses a star Name minimum 220 and remaining widths 110/120/140/100/100 (sum 570), whereas persisted defaults are 280/140/150/140/110/130. The runtime header uses preferred widths while an unconfigured row can absorb spare space into Name and use different later widths. This is a concrete mechanism to test, **not an established screenshot cause**. Similarly, a stale screenshot build or saved customization remains possible. Measure boundaries, not just glyph positions: trimming, text insets and progress centering can otherwise look like column shifts.

## Repeatable native checks requested

The sole native tester should record actual EXE/DLL/PRI hashes, preferences before each case, outer physical size, client DIP size and rasterization scale. Preserve existing records/preferences; use an isolated fixture or restore deliberate customization.

1. **Gaps/search drift:** with two rows and known widths, capture restore → maximize → restore, then widen beyond 1030 table DIPs. Record transfer viewport, canvas left/right, header left, search left/right and remaining toolbar star-column bounds. Compare canvas gap against viewport minus explicit canvas width. This separates measured centering from merely fixed sizing.
2. **Column mismatch/lifecycle:** record each header boundary and same row boundaries with two rows; filter down to one and clear; hide/reorder/drag a column; scroll enough existing/fixture rows to recycle, then return. Repeat when vertical scrollbar appears. Distinguish a constant origin delta from varying cumulative width deltas. If inspection can expose row ColumnDefinitions/Loaded state, record it; a screenshot alone cannot prove callback failure.
3. **Pane intent:** note saved and actual sizes wide; shrink then enlarge; edit an unrelated layout preference; compare sizes again. Separately resize one pane while the other is clamped, restart wide and compare saved values. This tests loss in effective state separately from later persistence.
4. **Shell/dialog reachability:** at 800 × 600 and candidate 560 × 420 client DIPs, test search focus/value, all toolbar/menu actions, sidebar labels/counts, history actions, details selection, footer, long notices and every dialog. Record clipping and remaining transfer height. Do not label 560 × 420 supported unless it passes after adaptation.
5. **Units:** repeat available display scales/monitor transitions and report unavailable cases. Compare physical boundary error after converting common DIP boundaries using recorded scale; acceptance is ≤1 physical pixel. Test short/wide independently of narrow/tall.

## Planned R1/R2 contract and thresholds

R1 should resolve one immutable layout version containing visible ordered IDs, preferred/effective widths, measured viewport, selection gutter, owned/measured template insets, scrollbar allowance and common rounded column edges. Both header and every realized/reused row consume that version before display. One horizontal scroll owner moves both; the finite-height virtualized ListView alone owns vertical scrolling. Header/row XAML must not supply competing fallback geometry. Keep stable selection and collection identity.

Fit mode: column budget = measured viewport minus common gutter/insets/occupied scrollbar. Allocate surplus to Name; reduce preferred extras toward semantic minimums deterministically; scroll horizontally if minimums do not fit. Manual mode: preserve preferred widths and anchor left; trailing background is deliberate. No further header-offset patch substitutes for owning native geometry.

Initial semantic minima from the responsive plan total 690 DIPs (180/100/120/110/90/90), plus 32 selection gutter and measured extras. All six columns therefore cannot fit without horizontal scrolling below roughly 722 table DIPs; a docked 160 sidebar + 6 splitter raises the rough full-client requirement to 888 plus remaining measured chrome. These are arithmetic design estimates, not native-supported minimums.

Keep 1100/800/560 client-DIP wide/regular/compact targets and 560 × 420 candidate minimum **provisional**. R2 should trigger measured content-fit fallback even above these thresholds: right-anchor search wide, full second row regular/compact, overflow secondary commands, overlay filters compact, preserve focus/filter values. At 800 with docked sidebar, deliberate table scrolling is expected under these minima. R3 must separate durable pane intent from temporary effective clamp/collapse; resize must not persist temporary state. Native results must confirm thresholds and minimum before R0 acceptance, and R4 must verify the full matrix.
