# Browser handoff protocol, state machines and acceptance matrix

Status: v1 contract reference and later-phase design constraints first written 2026-10-11. Package 8 has a disabled domain reservation implementation, not an accepted browser takeover protocol. Phase B direct-header feasibility is blocked. The first Phase C open-only slice is implemented locally; deployment acceptance remains pending (see [Phase C evidence](BROWSER_HANDOFF_PHASE_C_EVIDENCE.md)). Apply the current [Phase A/B review](BROWSER_HANDOFF_PHASE_AB_REVIEW.md) and [Sol handoff](BROWSER_HANDOFF_PHASE_AB_SOL_HANDOFF.md) before turning later-phase sketches below into wire actions. Numeric limits below are product choices, not browser limits; change both endpoints and tests together.

## 1. Transport rules

Browser ↔ host uses the browser native-messaging frame: unsigned 32-bit native-order byte length, then exactly that many UTF-8 bytes. On supported Windows x64 this is little endian. Host ↔ app explicitly uses unsigned 32-bit little endian with the same JSON envelope. Never use line-oriented JSON, text encoding BOMs or `ReadLine`. Read loops must handle partial headers/bodies and EOF. Only one writer may serialize a frame at a time. Browser protocol reference: [Chrome native messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging).

| Limit | v1 value | On violation |
|---|---:|---|
| UTF-8 JSON body | 64 KiB, inbound and outbound | Reject/close before allocating larger body; no echo. |
| JSON depth | 8 | `invalid_request` when a reply is safe. |
| URL UTF-8 bytes | 16 KiB | `invalid_request`; no truncation. |
| Filename | 240 characters plus existing Windows rules | `invalid_filename`; app can offer rename. |
| Request ID | UUID canonical string | `invalid_request`. |
| Installation ID | UUID generated by extension install, not synced | `invalid_request`. |
| In-flight native requests per port | 4 | `busy`, bounded retry. |
| App intake queue | 32 requests | `busy` before acceptance; do not discard accepted jobs. |
| Simultaneous host pipe sessions | 8 per selected installation | Refuse extra sessions with bounded error. |
| Pipe connect warm deadline | 2 seconds | `unavailable`, no claim about prior mutation. |
| Cold-start overall deadline | 15 seconds | `unavailable` or `unknown` depending on whether mutation was sent. |
| Individual request response deadline | 10 seconds | Query status with same ID; no new ID retry. |
| Per-frame read idle deadline | 5 seconds | Close incomplete/misbehaving connection. |
| Idle native port | 30 seconds | Close gracefully; reopen on next gesture/status query. |

Deadlines are wall-clock budgets with cancellation and capped exponential backoff; tests use injected time. Queue bounds prevent a webpage-induced gesture loop or malfunctioning extension from allocating unlimited work. The app does not trust a client-provided timeout to erase an accepted request.

Use a connection handshake before mutations. Protocol major mismatch rejects; additive minor fields can be ignored only where explicitly allowed. Unknown actions and unknown security-relevant fields reject. No arbitrary dictionary of engine options. Schema fixtures must be shared by C# and extension tests.

## 2. Envelopes and examples

All messages have `protocol`, `requestId`, `action` and `payload`; responses repeat the ID and carry `result`. A status query has its own correlation request ID and a separate target ID. Host supplies verified browser/extension context separately on the pipe, overwriting rather than trusting equivalent client fields. The extension's installation UUID distinguishes profiles but is not authentication.

```json
{
  "protocol": { "major": 1, "minor": 0 },
  "requestId": "e204774d-08ba-4a09-96c9-9e64f2b31ce3",
  "action": "hello",
  "payload": { "extensionVersion": "1.0.0", "installationId": "7df3ed34-ea26-450b-a428-90ce4c9589ec" }
}
```

```json
{
  "protocol": { "major": 1, "minor": 0 },
  "requestId": "e204774d-08ba-4a09-96c9-9e64f2b31ce3",
  "result": {
    "code": "ready",
    "appVersion": "1.0.0",
    "capabilities": ["addPublicGet", "getRequestStatus"],
    "maxMessageBytes": 65536
  }
}
```

```json
{
  "protocol": { "major": 1, "minor": 0 },
  "requestId": "9d72e0be-8cdd-41c2-9b20-a78e6060df41",
  "action": "addPublicGet",
  "payload": {
    "installationId": "7df3ed34-ea26-450b-a428-90ce4c9589ec",
    "createdAt": "2026-10-11T12:00:00Z",
    "sourceUrl": "https://downloads.example.test/releases/archive.zip",
    "suggestedFileName": "archive.zip",
    "trigger": "linkContextMenu"
  }
}
```

The example has no directory, cookie, referrer, user agent, page URL, browser download ID, bearer token, RPC endpoint or RPC options. None is required for explicit public GET. A missing filename is allowed: app destination logic suggests one and validates it. If the result would collide, return an actionable conflict; do not silently overwrite or attempt a second engine add.

```json
{
  "protocol": { "major": 1, "minor": 0 },
  "requestId": "9d72e0be-8cdd-41c2-9b20-a78e6060df41",
  "result": {
    "code": "accepted",
    "jobId": "4f8cbb4a-9b09-42f1-a21e-945718b95066",
    "state": "queued",
    "duplicate": false
  }
}
```

`accepted` means the app durably owns one job intent, not that bytes arrived, authentication worked or the server supports resume. UI: “Added to AriaGUI” with current job state. `engine_uncertain` is a job state after acceptance, not a signal to create a replacement. Do not return `success: true` as the only acknowledgment.

```json
{
  "protocol": { "major": 1, "minor": 0 },
  "requestId": "7dfeb36a-07cb-4ce0-a31e-8c97172b823d",
  "action": "getRequestStatus",
  "payload": {
    "installationId": "7df3ed34-ea26-450b-a428-90ce4c9589ec",
    "targetRequestId": "9d72e0be-8cdd-41c2-9b20-a78e6060df41"
  }
}
```

Status response codes: `accepted` (with stable job ID), `rejected` (stable reason), `processing` (bounded retry), `not_found` (no durable record in this selected installation), `expired` (tombstone exists but detailed result is pruned). Transport errors are separate from application results. A status query must be scoped to the same caller/installation, not expose all users' jobs.

Suggested rejection reasons: `unsupported_protocol`, `invalid_request`, `unsupported_url`, `invalid_filename`, `destination_conflict`, `destination_unavailable`, `integration_disabled`, `not_ready`, `shutting_down`, `busy`, `storage_unavailable`, `request_id_conflict`. Display text is locally mapped; never pass exception messages or source URLs verbatim through the bridge.

## 3. Durable idempotency and acceptance transaction

Proposed key: `(callerIdentity, installationId, requestId)`, with caller identity determined by native-host launch context plus its configured allowlist. A repeated key with the same canonical payload fingerprint returns the original job ID/result. The same key with changed URL/name/trigger returns `request_id_conflict`. URL-only deduplication is forbidden: downloading the same URL twice intentionally is valid. Conversely, generating a new request ID on each retry defeats idempotency.

Fingerprint exact accepted semantic fields including immutable `createdAt` using a deterministic serialization and cryptographic hash; do not normalize query order or decode signed URL escapes. Strip fragments consistently before both validation and hashing. Do not log the fingerprint as a public identifier; source URLs may be guessable and hashes are not encryption. For a previously unseen mutation, reject `createdAt` older than seven days or more than five minutes in the future. A retry preserves both ID and timestamp. Consult an existing ledger/tombstone first so a known accepted request remains queryable. This age gate prevents an honest stale client from creating work after compact tombstones have been pruned; timestamps are not an authentication mechanism.

Proposed `ExternalRequestRow` fields:

| Field | Purpose |
|---|---|
| CallerKey, InstallationId, RequestId | Composite unique idempotency key. |
| PayloadDigest | Detect conflicting reuse without storing a second raw URL. |
| JobId | Nullable before acceptance; FK or retained tombstone on history deletion. |
| State, ResultCode | Durable intake outcome independent of engine observation. |
| CreatedAt, AcceptedAt, UpdatedAt | Expiry/diagnostics with UTC clock. |
| ProtocolMajor, Trigger | Migration and policy evidence. |

The ledger and existing job/attempt/file/pending-add rows must commit in **one SQLite transaction**. Writing the ledger after `DownloadCoordinator.AddAsync` returns leaves a crash hole that can create duplicate jobs. A new repository operation such as `InsertExternalIntentAsync` is proposed; implement it in the existing database with a transaction, not a second independent database. Preserve unique destination and engine-ID constraints. Concurrent identical requests must converge at the database unique constraint, not only a process-local dictionary.

Refactor the coordinator into reusable validation/intent construction/dispatch stages while keeping a single authority for job state. The intake service obtains a stable receipt after commit; engine dispatch can then run under app lifetime, independently of the socket. The existing Add wrapper can await dispatch if required for its existing UX. Persisted-but-not-dispatched requests must be reconciled on startup using saved GIDs and existing recovery rules; do not blindly resubmit after an ambiguous engine call.

Ledger retention: keep accepted key→job mapping for the job lifetime; retain compact tombstones for at least 90 days after user history deletion. Extension retries expire after 7 days and then require a new deliberate action. Do not silently replay a months-old unresolved request. Rejections may expire after 7 days; a retried expired mutation must not create work automatically. Rejected/expired state semantics must be identical in both clients. History deletion must not cascade away idempotency evidence prematurely.

For protocol v1, do not implement an out-of-band “cancel handoff” that removes an accepted job. Cancellation of the native socket is transport cancellation only. The user manages accepted jobs in AriaGUI. A later job control API would require its own authorization and lifecycle design.

## 4. Explicit handoff state machine

```text
User gesture
  -> validate public HTTP(S) link
  -> allocate request ID; persist ID + installation + created time (no URL)
  -> connect/hello
  -> send addPublicGet
     -> rejected: show reason; user can use the original link
     -> accepted: record job ID; show Added to AriaGUI
     -> connection lost after send: mark outcome unknown; query SAME ID
          -> accepted: show original job
          -> processing: bounded query retry
          -> not_found: offer explicit retry using SAME request ID if URL is still in live gesture state
          -> still unreachable: show Cannot confirm; check AriaGUI before trying again
```

No automatic browser fallback download is initiated on an uncertain outcome. “Fail open” here means the original browser behavior was never canceled; context-menu selection itself does not promise a browser download has started. An unavailable host gives installation/repair guidance, while preserving the link and page.

On worker restart, read unresolved nonsecret IDs and query the app. Do not store URLs in extension local storage just to replay them. If a payload was never sent and is no longer available, mark it expired/not submitted and ask for a new gesture. An accepted job remains in the app even if extension storage is cleared.

## 5. Later automatic takeover protocol

Do not include these actions in v1 advertised capabilities. They are a specification direction for a separately reviewed phase.

1. Establish eligible replayable public GET through a trusted controlled-source contract and policy consent; bind grant issuer/policy revision, exact source/context, expiry and browser item ID + start time + profile identity. A URL allowlist or `onCreated` alone does not establish method/replayability.
2. Persist a minimal pending recovery record before any first browser side effect, including pause. Optionally pause the browser, handling errors and immediate completion. An unpause failure is not hidden. Do not persist raw source URLs or headers in extension storage.
3. `prepareTakeover` validates/reserves an app destination and persists a prepared request with expiry, but issues **no network request** to the origin and no active aria2 job. A HEAD/range probe can consume one-time resources and is not a universal validation.
4. Re-read browser item. If complete, unsafe, missing, changed incompatibly or no longer eligible, `abortPrepared` and leave browser result alone.
5. Persist cancellation-requested state, request browser cancellation, then re-read fresh item state/error and unchanged identity. Each browser adapter must map its specific canceled outcome; a fulfilled call, missing item or unrelated interruption is insufficient. If completion won, abort. Ambiguous outcomes remain unresolved or abort where safe; never silently restart a browser transfer whose cancellation/commit outcome is unknown.
6. After confirmed cancellation, send `commitPrepared` with the same request ID. Commit atomically produces accepted job intent and makes the app responsible for recovery. If acknowledgment is lost, query that ID. Never allocate another job.
7. If canceled but commit cannot be confirmed, keep a durable pending recovery record and visible status; recover by status query and idempotent commit. If the reservation expired uncommitted, offer a deliberate browser restart or new app transfer and explain that browser bytes may be lost.

Prepared expiry is 60 seconds by app clock; commit/abort/expiry race under a transaction. Commit wins once durable; abort never removes accepted work. A prepared entry performs no aria2 network action and expires without creating a queued job. If the extension knows the browser was canceled but cannot reach the app before expiry, loss-free recovery is not guaranteed. This is the explicit residual risk that gates release.

The disabled domain implementation uses UTC deadlines, not a physical sixty-second erasure promise. Clock rollback can lengthen real elapsed lifetime. Startup, ten-second periodic maintenance and wake cleanup each process at most 64 expired rows; a commit independently checks its own deadline. Clearing live intent does not erase SQLite/WAL/backup bytes. A0 quotas and retention evidence are in [the review corrections report](BROWSER_HANDOFF_A0_B0_EVIDENCE.md).

Future takeover wire results must separate durable state from query/error outcomes; do not serialize the internal domain enum wholesale. A retained committed request whose history was deleted reports committed responsibility with an expired tombstone receipt and no live job ID. It never reauthorizes an Add. Recovery must rehydrate source/name from the same unchanged browser item or an explicitly reviewed identity-bound app reference. Missing/changed source evidence ends in truthful cannot-confirm guidance, not a fresh request key.

After app acceptance, do not auto-remove the job merely because the browser still looks interrupted. Do not erase browser history. Never delete browser partial files from the host. A new aria2 transfer starts at zero; only its own data/control file can later resume under the app's recovery policy.

## 6. Crash/failure matrix

| Failure point | Durable evidence | Required result |
|---|---|---|
| Host missing before send | No app mutation | Clear unavailable/install message; browser unchanged. |
| GUI launches slowly | Possibly no pipe yet | Bounded retry; one launch; no duplicate app/engine ownership. |
| Preference/database init fails | Not ready | Reject intake; do not substitute an arbitrary folder. |
| Client disconnects before transaction | No accepted ledger/job | No work, or status processing until in-flight validation ends; cancellation must be defined before commit. |
| Crash inside transaction | SQLite all-or-nothing | Either no ledger/job or both; never orphan acceptance. |
| Crash after commit before reply | Ledger + job | Retry/query returns same job; startup recovers intent. |
| Crash after engine mutation before observation | Ledger/job/GID; uncertain operation | Reconcile same GID; no blind second Add. |
| App accepted but engine offline | Durable queued/uncertain job | Show accepted with truthful state; app owns recovery. |
| Repeated event/message | Existing key | Same receipt, `duplicate: true`; one engine intent. |
| Same key altered payload | Digest mismatch | Reject conflict; original job unchanged. |
| History deleted then old retry arrives | Tombstone | Expired/original outcome; never recreate automatically. |
| Worker dies during explicit request | ID in extension storage | Query app after wake; no new ID. |
| Browser completes before automatic cancel | Browser complete | Abort prepared app entry; no new transfer. |
| Browser canceled then app unreachable | Browser evidence + prepared/unknown app | Visible recovery; no claim of perfect fail-open. |
| Shutdown races new request | Admission barrier | Rejected before commit or accepted and recoverable; no false ACK. |
| Installer updates while host active | Versioned files / protocol handshake | Existing process finishes; next uses compatible host or reports mismatch. |

## 7. Test and acceptance matrix

Use synthetic origins and profiles. No test should need real session cookies or a personal browser profile. Add deterministic fixture routes and test-specific runtime/installation descriptors. Log only safe codes/IDs; keep synthetic marker values in test assertions.

| C02 | Zero/oversized length, invalid UTF-8/JSON, deep nesting, EOF | Bounded memory, deterministic rejection/close, host alive where safe. |

N03 is a real acceptance requirement, not a claim the current engine automatically enforces all HTTP validators. If the current pipeline cannot establish entity continuity, document that limitation and prevent unsafe auto-resume claims. Browser handoff must not weaken existing file preservation.

For N01/N02 interpretation, HTTP byte-range support is a server protocol capability, not a browser-extension feature. The aria2 configuration and control-file recovery determine its behavior; inspect requests and final hashes with the fixture rather than assuming a successful UI progress bar proves resume. ## 8. Release evidence

Later [A1 fixture evidence](BROWSER_HANDOFF_A1_EVIDENCE.md) covers browser-independent state/recovery and injected Chrome/Edge/Firefox snapshot mappings. These modules are not packaged, and no real browser test was run. A01–A04 remain unaccepted; new transport/permissions and automatic takeover remain gated.

A subsequent [narrow real-browser probe](BROWSER_HANDOFF_A1_REAL_BROWSER_EVIDENCE.md) passes controlled Chrome/Edge API observations and records Firefox's failed temporary-addon installation through available automation. It is separate from the fixture milestone and does not pass A01–A04 or enable a new transport capability.

Each supported browser needs a recorded version, extension build/hash, host/app build/hash, selected installation channel, OS architecture and pass/fail for the matrix subset it claims. A Node unit suite is not evidence that real browser native messaging installation works. A developer-machine success is not clean-machine installation acceptance. Record deferred capabilities explicitly in the release note; never mark cookie or automatic-capture rows passed because the feature is disabled.
