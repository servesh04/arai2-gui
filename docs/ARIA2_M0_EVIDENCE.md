## Reproducible experiment

Run `python scripts/Probe-Aria2M0.py --output artifacts/m0/engine-probe.json` in an environment that permits fresh loopback sockets. The script starts only the pinned executable, a synthetic 8 MiB loopback origin and authenticated RPC on independently selected private ports. It creates a temporary runtime below `artifacts/m0`, removes it on exit and terminates its child engine. No application engine, app data, browser profile or handler is opened. `artifacts/m0/engine-probe.json` records every request interval, response status, bytes sent, completion/cancellation and relative timing, plus RPC observations and byte hashes. It contains no origin secret or signed URL. The sandbox initially denied loopback RPC with WinError 10013; the successful run used approved local socket execution.

Evidence JSON SHA-256: `F55C9BF775FE9C50342548EBE1D4FDA73FDB1A1492E8AC7F4CE5C5144CB78560`. The script's assertions passed for simultaneous engine ranges, sparse file, stable paused bytes, GID continuity, rate-option confirmation, final exact bytes and duplicate bounded-zero origin responses. `engine_bounded_zero_206=false` is an observed negative result, deliberately recorded rather than treated as a failed safety assertion.

## M0 decisions and next gates

The compatibility specification for historical attempts remains a single-source sequential HTTP attempt: connection count 1, no expected publisher digest, existing origin provenance and current journal versions. Future immutable typed records should bind transfer kind, source set, destination manifest, integrity requirement, origin policy and connection/bandwidth policy to one attempt revision. Readers must explicitly map legacy attempts to this specification; no generic engine options dictionary or implicit upgrade of completed history is acceptable. No production contract or dispatch was changed in M0 because a stored spec without its migration/recovery reader would be unsafe.

Classify prospective options as follows: DHT/PEX/LPD and listener/network posture are startup ownership policy; `max-download-limit` is a live engine mutation requiring observed confirmation and upstream measurement; `split`/`max-connection-per-server` are restart-causing reconfiguration, requiring durable intent, pause/quiescence and exact partial/control preservation. The first shipping adaptive policy may choose an initial count between 1, 2 and 4 only after M3; live changes remain separately gated.

Provisional M3 experimental limits, fixed before performance claims: at most 4 connections per attempt, 8 across owned attempts, 4 to one actual origin; at most one 8 MiB response interval and 64 KiB of response metadata/header budget; known length, strong validator and identity encoding required. A benchmark is not an acceptance pass unless each request's interval/validator/bytes, simultaneous overlap, final bytes, control snapshot and retained-pair preservation all pass. Throughput benefit is considered only after correctness and must exceed 20% sustained over a single-connection baseline without a greater than 10% regression on the control origin. These are proposed review thresholds, not implemented limits.

**M0 stop decision:** keep sequential HTTP and production flags as they are. The pinned engine supports concurrent bounded nonzero ranges, but the present gateway serializes a whole response, ignores a requested end, and returns 200 for offset zero. Sparse writes invalidate length-only checkpointing. M3 must replace those boundaries and prove crash/recovery before any fixed or adaptive parallel dispatch. M1 and M2 can proceed independently under their own gates.
