# Browser companion installation (development only)

The existing MSIX pipeline is unchanged. Browser integration is a separate x64 unpackaged companion bundle. `Install-BrowserCompanion.ps1` implements reproducible staged install/repair/readback/uninstall under an explicitly selected synthetic workspace UUID. Production per-user application of that flow to a stable private directory such as `%LOCALAPPDATA%/AriaGUI/Browser/<channel>`, trusted GUI/runtime/descriptor generation and exact browser HKCU registration remain blocked. Moving the directory requires manifest regeneration and explicit repair. This package supplies a tested synthetic installation transaction, not a release-enabled installer.

Production/browser traffic is disabled. Release registration is not accepted; development registration currently supports dry-run/readback only. Applied verification uses only `HKCU/Software/AriaGUI/Verification/<random UUID>` with a unique synthetic host name, which browsers do not discover. Neither tool installs an extension, touches browser profiles, changes HKLM or falls back to another browser's registry root.

```powershell
# Existing self-contained x64 native-host publish is an input, never rebuilt implicitly.
./scripts/New-BrowserBundle.ps1 -HostPublishDirectory <publish> -OutputDirectory <NEW artifacts/browser-packages/directory>
./scripts/Register-BrowserHost.ps1 -Channel development -Browser chrome,edge,firefox -InstallRoot <bundle> -Action install
./scripts/Register-BrowserHost.ps1 -Channel development -Browser chrome -InstallRoot <bundle> -Action readback
# Synthetic file staging only, no registry operation. Run from the checkout scripts directory.
./scripts/Install-BrowserCompanion.ps1 -Action install -Channel synthetic -SyntheticWorkspaceRoot <artifacts/browser-installer-tests/UUID> -InstallRoot <workspace/stable-payload-folder> -SourceBundle <synthetic-bundle> -Apply
```

No `-Apply` means dry-run. The plan contains exact selected browser roots, both32/64 registry views, host/manifest paths and channel; readback explicitly returns Connected=false. Edge uses its own key, never Chrome fallback. Repair refuses a foreign default value. Failed install/repair restores the captured default value only while it still equals this operation's pointer; concurrent changes are preserved and reported. Uninstall removes only this exact owned REG_SZ pointer and deletes a key only when otherwise empty. Non-default values/subkeys are retained. No recursive filesystem uninstall is provided; app history/runtime is never a bundle member or cleanup target. Registry views may alias HKCU Software, so restoration/removal is idempotent across views.

Every invocation revalidates bundle integrity and rederives its plan; changed manifests/root/entries after dry-run fail closed. Uninstall does not claim an atomic multi-key transaction: a mid-removal failure reports partial completion and can be retried for remaining owned pointers. Missing/moved/corrupted bundle currently blocks automatic uninstall as well; verified repair is required. Registry ownership checks are immediate read/compare operations, not an OS atomic compare-and-swap against malicious same-user races.

Synthetic file installer uses a private sibling stage, validates the copied source before allowed native-path rewrites, verifies the resulting inventory, refuses active payload processes, switches directories with a rollback backup and preserves its external ownership receipt/installation ID on repair. A post-switch injected failure restores payload and receipt. An exclusive operation file prevents cooperating concurrent installers. Every recursive move/delete is resolved and checked inside the selected synthetic workspace; payload removal also requires complete matching inventory and ownership receipt. Unknown extra files block uninstall. Runtime/history outside the payload are preserved. Abrupt OS/process termination during the multi-file switch/receipt phase is not a proven crash-atomic transaction; leftover stage/backup/orphan receipt requires verified recovery rather than blind cleanup. Active-process inspection is best effort plus Windows file-lock behavior; malicious same-user races are not defeated. No executable trust/signing claim is made.

The receipt's companionInstallationId is an installer ownership identity, **not** the app runtime UUID carried in v1 installationId. No descriptor/runtime UUID is generated by staging; the future trusted installer must select the actual app instance. Reinstall after full uninstall creates a new companion receipt identity while preserving outside app history. Dry-run performs source integrity, containment, active-process and existing receipt checks without creating directories or locks.

Generated bundle includes host/runtime files, extension ZIPs/directories, exact development native manifests, registration/staging tool sources, matching restored .NET runtime declared notices/dependency inventory and SHA-256 inventory. Host descriptor and GUI/runtime/profile are deliberately absent; the host therefore fails closed. Unsigned inventory detects accidental content changes, not hostile replacement or trusted provenance. Full .NET/native notice redistribution review and signing remain pending. Synthetic staging tooling runs from the source checkout; shipping it does not enable a production installer path.

Settings store disabled-by-default browser metadata independently from existing theme/folder/layout. The enable checkbox remains disabled. The readiness check can report missing selected metadata/host and release-blocked state; no production hello transport is composed. A ready result requires a strictly validated correlated compatible hello, never a registry value; extension presence cannot be established by a GUI-only check. The existing extension Test connection is the browser-side hello path after a future trusted setup.

Unverified: clean-machine host/GUI dependencies, a real stable-path installer, running-host update/rollback, signing/store/privacy review, MSIX host discoverability/version replacement, actual Chrome/Edge/Firefox accepted-download and private-context acceptance, per-extension ledger isolation and DNS/redirect safety. Do not advertise any package/browser combination as production-supported from these development tests.
