## Current boundary and compatibility decision

The pure launch classifier admits exactly `Plain` (zero arguments), `BrowserWake` (one case-sensitive `--browser-wakeup`) or `OpenUri` (one case-insensitive `ariagui://open` or `ariagui://open/`). All other argument vectors are rejected. The installed native-host descriptor and GUI share `GuiLaunchContract.IsBrowserWake`; application tests assert that compatibility, and copied-GUI cold/warm wake launches were measured. EngineFixture's `--bridge-auto-host` remains rejected by the GUI. OS Protocol activation remains restricted to the open parser.

Validation is lexical **on the delivered value**, before app-side decoding/normalization. Windows/browser processing can precede delivery. The explicit canonical capture experiment verified that Windows ShellExecute turns `ariagui://open` into `ariagui://open/`; accepting that single root-slash form was authorized after this measurement. Extra paths/slashes, queries, fragments, ports, userinfo, encoded action alternatives and extra arguments remain rejected. No production URI/argument payload is stored or logged. DEBUG/verification copied payloads emit only PID, activation kind and supported/rejected booleans.

`SingleInstanceLease` remains the GUI owner and engine ownership/recovery is unchanged. The independent Win32 receiver uses a payload-free user/runtime-scoped wake. HWND publication is a routing hint, not authenticated lease-owner proof. Foreground permission is granted only to the matching scoped window PID, and Windows can refuse focus. Requests have no ACK; startup broadcasts can be lost and closing owners ignore requests. A deliberate launch after shutdown is the recovery behavior.

The controller bounds its own UI callbacks/startup latch to one, with 500 ms admission spacing and a 30 second pending lifetime; it does not bound OS launcher creation or the Windows message queue. Ordinary cold activation shows the window through normal startup; controller readiness tests are separate domain fixtures. Closing stops admission before cleanup, with the lease released last. A bounded, marked verification-only shutdown hold now permits an actual GUI interleave check; normal Release excludes this hold and all fixture receipts.

## Registration and measured OS boundary

Packaged registration uses one `windows.protocol` manifest declaration named `ariagui`; the declaration selects a scheme, while the app enforces open-only action. The standalone unpackaged registration helper is explicit and dry-run-by-default with command `"EXE" "%1"`; it refuses foreign/changed ownership and unregisters after executable removal. That helper alone has no installer journal. The later narrow installer review candidate now supplies a fixed per-user path and cooperating-process serialization/recovery (see below). Neither tool forces UserChoice/default selection or provides compare-and-delete against other registry writers. Browser companion installation does not own this GUI association. Shipping shortcut/bootstrapper distribution and actual isolated installer acceptance remain release decisions/gates.

Microsoft guidance supports manifest registration for packaged applications and explicit registration for unpackaged applications; reading AppInstance activation does not require replacing GUI ownership. Foreground permission is best effort. Sources: [URI activation](https://learn.microsoft.com/en-us/windows/apps/develop/launch/handle-uri-activation), [rich activation/registration choices](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/applifecycle/applifecycle-rich-activation), [foreground permission](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-allowsetforegroundwindow).
