# Browser handoff Package 4: bounded native host

2026-10-12; base `ce1f333`. Adds the Windows x64 console host and synthetic process evidence. No browser registration, extension installation, installer mutation, personal profile, or production listener activation occurred. Production browser intake remains disabled.

## Trusted configuration and invocation

`src/AriaGui.NativeHost` references Contracts/Core only. Its fixed adjacent `native-host.v1.json` is an installer-generated descriptor, not browser JSON or an environment-selected configuration. Pascal-case fields are `SchemaVersion`, `Mode`, `InstallationId`, `Channel`, `PackageModel`, `RuntimeDirectory`, `HostExecutable`, `GuiExecutable`, `GuiSha256`, `MinimumAppVersion`, `AllowLaunch`, `LaunchArguments`, `ChromiumOrigins`, `FirefoxManifest`, and `FirefoxAddonIds`. SchemaVersion is 1. Descriptor/Firefox manifest are limited to 16 KiB/depth 4, reject duplicate properties, and the descriptor rejects unknown properties. Paths are absolute/local; reparse files/ancestors and broadly writable descriptor/target parent ACLs are rejected. Owners/writers must be current SID, SYSTEM, or Administrators. The selected GUI hash and private persisted UUID must match. Same-user replacement is outside this protection; this is not an Authenticode/signature verifier or a complete installer.

Installed mode permits only release/unpackaged and fixed `--browser-wakeup`. That future GUI launch mode and production activation are not delivered here. Debug verification descriptors require a marked synthetic runtime and fixed fixture launch arguments; Release rejects verification descriptors. Tests create these files only under a private temporary fixture root. No command line or browser payload can select a descriptor, runtime, GUI, or pipe name.

Chromium adapters accept an exact configured `chrome-extension://<32 a-p characters>/` origin plus one syntactically valid decimal `--parent-window=` argument. Chrome and Edge use the same documented Windows invocation format; the argument format does not prove which browser launched the process. Firefox separately requires the exact selected manifest path and allowed add-on ID, and checks manifest `type`, `path`, and `allowed_extensions`. Browser arguments are defense in depth, not authentication against same-user local command invocation. Formats follow [Chrome native messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging) and [Firefox native messaging](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Native_messaging).

`BridgeEndpointName` moves the unchanged Package 3 endpoint algorithm into Contracts for both peers. The host reads the existing UUID and never creates a replacement. Before any pipe request, it checks the kernel-reported server PID, process token SID, exact selected executable path and SHA-256. An internal correlated hello must report compatible major/minimum app version, 65,536-byte limit and both required capabilities before mutation forwarding. This proves the selected executable process, not its signer or browser provenance.

## Bounds and ambiguous outcomes

Native stdin/stdout are binary framed; stdout contains only closed v1 response envelopes. The host shares Contracts exact-read/strict JSON/UTF-8 validation. Native whole-frame receive and write have five-second await bounds, including idle waiting; console stream reads that do not honor cancellation cannot indefinitely hold the main session. Session lifetime is 60 seconds, maximum 16 native requests, one in flight. These idle bounds are deliberately stricter than the proposed 30-second idle limit.

Connect budgets are two seconds warm / fifteen seconds cold; at most three connection generations, bounded retry attempts and a single fixed GUI launch per host. It reconnects after seven relayed requests because the bridge's eight-frame limit includes internal hello. Child output is discarded using a fixed buffer and 64 KiB cap, never mixed into native stdout; the host does not kill a launched GUI. Diagnostics are fixed codes only, without request bodies, URLs, filenames, credentials or raw exceptions.

The host sets its mutation ambiguity flag before the first Add frame write. Disconnect, partial write, wrong response correlation or lost ACK thereafter yields `unknown`, with no automatic Add replay. Connection/identity/hello failure before mutation and status transport failure yield `unavailable`. A future extension must reconcile using the same stable request ID. No new result or identity schema was introduced.
