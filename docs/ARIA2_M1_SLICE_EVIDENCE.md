# M1 bandwidth policy, per-job cap and schedule slices

2026-10-14, continued 2026-10-15. Aggregate download/upload caps, per-job download caps, and runtime-only weekly schedules have application APIs and durable policy state. Preferences exposes a saved named-profile catalog, per-job controls, a multi-interval weekly editor, and expiring override controls.

## Implemented path

`ByteRateLimit` represents unlimited explicitly as `null` and accepts bounded positive byte rates; zero is rejected at the application boundary. `BandwidthProfile` names a download/upload cap pair. `BandwidthPolicy` stores requested and confirmed revisions, both profile values, the confirmed engine session and a pending/uncertain/failed status. `JobBandwidthPolicy` binds the same revision/status model to a durable job ID. Additive SQLite migrations `20261014154900_BandwidthPolicy` and `20261014160255_JobBandwidthPolicy` use the existing verified pre-upgrade backup path.

`DownloadCoordinator.SetBandwidthProfileAsync` commits intent before RPC. It sends typed `changeGlobalOption` values through the authenticated owned engine, reads the effective global values, and confirms only an exact pair. A lost response remains uncertain and is never sent a second time by polling. A definite rejection remains visible as failed and can be superseded by a new request. A later authenticated observation can reconcile uncertain intent, including after a new engine session. Same-session drift from a confirmed value becomes uncertain without an automatic duplicate command. The profile is exposed in `DownloadRuntimeSnapshot` for the Preferences editor.

Fresh engine startup writes the persisted requested caps into private aria2 configuration before its restored transfers are resumed. Verified surviving-engine adoption checks the stored policy and applies it before resuming saved intent. Failed requests use the last confirmed caps. The initial historical policy is unlimited in both directions, so existing jobs retain their prior behavior. Queue concurrency and split remain separate; the existing one-connection guarded dispatch was not changed.

`SetJobBandwidthAsync` commits a job-specific rate intent before RPC, requires the current nonterminal job and GID, and observes the effective `max-download-limit` through typed `changeOption`/`getOption`. The manager checks the repository's current job/GID; direct transport also checks exact RPC source/file ownership, and guarded transport requires ledger ownership for the same job and attempt IDs. The saved cap is included in `addUri` options for new/retry attempts. On fresh engine restore, every eligible entry is paused while its saved job rate is applied and observed, before normal resume intent is considered. Verified surviving-engine adoption follows the same order. Unknown or terminal entries are not mutated. Polling reconciles uncertain responses without resending and marks same-session drift uncertain.

`BandwidthSchedule` stores an explicit timezone ID, default profile, weekly local-minute intervals, an optional temporary override with UTC expiry, and an enabled bit. Validation rejects overlap including Saturday-to-Sunday wrap. Each evaluation converts the current instant to local wall time, so nonexistent DST intervals never run and repeated local intervals apply twice; no missed boundaries are replayed. `SetBandwidthScheduleAsync` persists configuration before applying it. Disabling stores a one-shot default-profile reset intent and clears it only after the owned engine confirms the default cap; startup also stages that intent after a crash. The existing coordinator polling loop reevaluates it while running, and `NotifyWakeAsync`/`NotifyClockChangedAsync` force a refresh. A schedule block issues pause intent without changing `DesiredPaused`, while `PolicyHeld` records the separate durable hold. Manual pause on an already held or in-flight hold strengthens user intent without another RPC. On release, only paused policy-held work without user pause resumes; removal and pending/uncertain operations are skipped. Fresh Add and Retry stage `PolicyHeld` and `StartPaused` before `addUri`, so a Block interval cannot begin with unpaused transfer bytes. Recovered jobs also start paused while a schedule is enabled. Fresh engine restore and verified adoption stage current scheduled caps and hold restored transfers before resuming any work. Migration `20261014161204_BandwidthSchedule` adds nullable schedule JSON to the aggregate policy row and the attempt hold bit.

The guarded loopback gateway shares one monotonic token bucket across all relay routes. It reserves the aggregate download budget before reading each origin body chunk, with a maximum 32 KiB burst, and refunds short reads. Startup and adoption seed it from durable policy before transfers resume. `ApplyBandwidthAsync` updates the same limiter when the profile changes. Aria2 still enforces the cap on its loopback receive side; the relay limiter bounds origin read-ahead across concurrent jobs. The shipping app uses `Aria2ProcessOptions.ForApplication`, which sets `UseContinuityGateway=true`; the manager refuses an adoption whose guarded-mode identity differs. Explicit direct-mode hosts have only aria2 receive-side caps, as measured below.

The saved catalog is an optional, validated `SavedProfiles` list in the existing schedule JSON value: up to 32 unique names, preserving old JSON and avoiding a schema migration. `SaveBandwidthProfilesAsync` persists the catalog under the schedule gate without applying an engine option. Schedule writes preserve the catalog. Preferences can select, save and delete named profiles; select a live job and apply its download cap; and add, replace or remove minute-precision weekly intervals with timezone ID, a chosen outside-interval default, block/profile actions and expiring override. Overlap validation happens before a schedule is committed. Disabling the schedule retains its intervals. The existing Win32 window subclass now forwards `WM_TIMECHANGE` and `WM_SETTINGCHANGE` to `NotifyClockChangedAsync`; the existing resume callback refreshes after wake. Periodic polling remains the fallback if tray registration is unavailable.
